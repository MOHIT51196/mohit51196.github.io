Why Microservices are not always the best choice

Detailed discussion on the trade-offs with microservices architecture

Jan 26, 2023 · 3 min read

Among the tech companies these days , Microservices architecture has became the de facto while designing a system. This architectural approach has gained popularity after the tech gaints like Uber, Airbnb, Facebook etc started using them.

Whats so good about Microservices

Microservices has multiple advantages over Monolith architecture as it allows the system to broken down into smaller components called serviceswhere each component handles a single responsibility and can be scaled up or down as per requirement individually. This kind of design offers low coupled independently deployable services which are highly easy to maintain and test individually.

Great power comes with great responsibilities

Because of this trending architectural approach, it is highly likely that if you are running a small startup or company and looking to build a software platform, your CTO or Technology head would suggest you to use microservices. After being a revolutionary architectural approach, this article will talk about why microservices are not for every one.

Microservices are recommended for large complex system which requires scaling. While designing microservices, one of the primary focus is on scalability. Incase the organisation is small and aware that a particular software is not made for handling huge traffic or does not require to work on large scale then Monolith is probably the best idea rather than microservices. Lets discuss why?

Microservices are not free lunch

Expensive to build initially

Multiple services means multiple deployments, which require multiple resources. Hence the upfront cost of deployment is higher as compare to monolith system.

Inter service communication

Microservices are much harder to design correctly. Multiple services are like multiple moving parts in a machinery which is trying to talk with each other. As the calls between different service are over a network, hence inter service communication needs to be handled correctly. Designing proper inter service communication may require you to setup internal rate limiters, message queues, caches etc.

Global testing is a challenge

As the software system disintegrated into multiple services which are further distributed on multiple nodes. Testing individual services are much easier but testing the complete system is harder as you require access to each and every component which are separately deployed. Testing the whole microservices based system is much harder than monolith.

Debugging challenges

Logging and monitoring needs to configured for each individual service and it is much harder to track & debug an issue in a distributed microservices architecture as there are multiple moving parts in a machinery.

Security challenges

As multiple services are deployed in containers separately, more of your system is exposed to the network as compare to the monolithic approach. It’s also worth noting that because containers are highly-replicable, one weak spot in one module can turn into a bigger problem. Hence without rights tools and security setup, maintaining security in microservices can become a nightmare.

Conclusion

Microservice not doubt has great advantages over other architectural approaches like event driven architecture, monolithic architecture, service based architecture. Microservice become highly cost effective and efficent in a later stage when the system scales upto handle millions of users or it comes highly complex. But in the intial days to need to pay in advance by putting much more effort in designing and developing it.

Incase you developing a system which is not meant to be scaled up for significant amount of users. You should probably rethink before using microservices, as monoliths can be much more useful in that scenario.

“ In world of software engineering, you need to understand that there cannot be a single generic solution for all of kind of use cases. Microservices are meant for scale and using it unnecessarily can be expensive and troublesome “
